# Format Version 0

## Brief

Version 0 is first edition on Binarium format. It defines the file structure, used algorithms and basic data types.

Binarium is a key-value map based archive, with performant O(log n) lookup. 
It is designed for robust and efficient binary serialization and deserialization of possibly big data blocks.
The format allows easy, zero-copy reads, with minimal application state 
(This repository official binarium viewer object implementation is only 72-bytes long), 
making it good fit for real-time applications storage format. 
A compression method is also embedded into Binarium, so it is convenient for big data.

Advantages listed above, comes at the price of file modification complexity; 
Adding or modifying an entry requires building brand new archive, as insertions are inefficient;
The format is immediate and not retained.

## Definitions

1. Binarium file is a key-value map. Keys are up-to 255 characters long ASCII strings, called *entries names*.
    Values vary on *entry data type* and are called *entries content*. A single pair (key, value) is named *entry*.
2. Whenever we say ASCII-string we mean a sequence of ASCII characters from printable range ``[32-126]``. 
    ASCII string does not have to end with termination character ``\0``, as Binarium does not use null-termination (see details)
3. *Section* is a part of file with unique layout
4. By *aligned* we mean align from beginning of the file
5. Float64 is floating point value as definied in IEEE 754 binary64

## Specification Details

1.  Little Endian is used all over the file
2.  Entry names must be unique; Empty names are allowed
3.  Null termination is not used anywhere, as byte lengths are known
4.  ASCII strings (names and labels) must be validated to consist only of allowed characters
5.  Padding bytes must be 0-initialized, so checksum is deterministic. Readers must reject files with non-zero padding bytes,
        otherwise one content would have many valid encodings and padding could carry hidden data
6.  There is exactly one valid encoding of a given set of entries (*canonical form*): entries order, names, offsets,
        paddings and lengths are fully determined by the entries themselves. Readers must reject files not in canonical form
7.  Floats are bit-copied, as cast to int64, from machine, NaN preserved
8.  Data offset of zero-length entries shall be in contents section, and shall not be within other entry range
        (in canonical form it is the offset the following chunk begins at, see *Contents*)
9.  Due to possible overflow entries count is capped at ``16'777'215``. Files with higher count are considered malformed.
10. The file ends exactly at the last byte of the *Footer*. Any byte after it makes the file malformed
11. Data type enumerators outside of the table in *Data Types* are malformed in version 0
12. Readers must reject files with ``version`` other than ``0``. Such files are unsupported rather than malformed
13. All sizes, offsets and counts read from a file are untrusted. Readers must not overflow, and must not access
        outside of the file, whatever the values are
14. Magic value is same in header and footer.

## Implementation Notes

1. Whether to uncompress data is user concern, user shall be able to read ``uncompressed size`` value before uncompressing
2. ``uncompressed size`` is untrusted. Allocation of the buffer for uncompressed data is user concern, and user shall put
    a limit on it when reading files of unknown source
3. ASCII strings may be empty
4. Readers are expected to validate everything listed in *Malformed Files* once, when opening the file, so later reads
    need no further checks. The only exceptions are compressed frames, which are checked when uncompressed
5. Readers must keep the file bytes unmodified for as long as they hand out views into them

## Names Lexicographic Order Algorithm:

Entries lexicographical order is defined by the following algorithm:

```cpp
Let a and b be compared names.
Let y[x] be x-th ASCII character of y name.

// Walk characters to find first difference
for (i = 0; i < min(length(a), length(b)); i++) {
    if (a[i] < b[i]) return <a comes first>;
    if (a[i] > b[i]) return <b comes first>;
}

// Case of one name being second prefix
if (length(a) < length(b)) return <a comes first>;
if (length(a) > length(b)) return <b comes first>;

// Case of names being equal
// Causes error on write (names must be unique)
// Allows binary search on read
return <equal>
```

## Sections

| Name      | Position                                  | Function                              |
| --------- | ----------------------------------------- | ------------------------------------- |
| Header    | Beginning of the file                     | File information and metrics          |
| Index     | After the header, aligned to 8 bytes up   | Stores entries info, sorted by name   |
| Names     | After the index, no align                 | Stores entries names                  |
| Contents  | After the names, aligned to 8 bytes up    | Stores entries values                 |
| Footer    | After the contents, aligned to 8 bytes up | Contains checksum value               |

Sections are in the order above, and nothing exists between or after them but the alignment padding.
For empty file (no entries) Index, Names and Contents are empty, the file is 48 bytes long.

## Header

*Header section* stores information on how to interpret rest of the file.

| Offset | Type     | Name      | Meaning                        |
| ------ | -------- | --------- | ------------------------------ |
| 0      | uint8[8] | magic     | Magic sequence for correctness |
| 8      | uint64   | version   | Binarium format version        |
| 16     | uint32   | entries   | Entries count                  |
| 20     | uint32   | names     | Names section length           |
| 24     | uint64   | content   | Content section length         |

* *Content section length* means bytes between first entry first byte to last entry last byte, 
    including inner paddings, without the section ones (the align after *Names* and before *Footer* sections).
    That is, it is ``data offset + data bytes`` of the last entry in the *Index*, or ``0`` if there are no entries.
    For a zero-length last entry it includes the padding before that entry
* *Names section length* means sum of all names lengths plus size of their length descriptors
* *Content* field is at offset aligned to 8 bytes to allow easy read on all architectures

## Index

*Index section* stores entries information, with entries ordered by their names lexicographical order.

Following is a single entry layout:

| Offset | Type     | Name          | Meaning                                               |
| ------ | -------- | ------------- | ----------------------------------------------------- |
| 0      | uint32   | name offset   | Entry name byte offset from begin of *Names* section  |
| 4      | uint32   | data type     | Data type enumerator                                  |
| 8      | uint64   | data bytes    | Data length in bytes                                  |
| 16     | uint64   | data offset   | Data offset in bytes from *Content* section begin     |

*Index section* consists of above structure, tightly packed, repeated ``header:entries`` times.  
*Index* entries must be ordered by corresponding names lexicographical order, with it defined as follows:  
*Name offset* of the first entry is ``0``. *Name offset* of every following entry is *name offset* of the previous
entry plus ``1`` plus length of the previous entry name, so entries names are in the *Names section* in the *Index* order.

## Names

*Names section* stores entries names in lexicographical order.
Following is a single name layout:

| Offset | Type         | Name          | Meaning                                               |
| ------ | ------------ | ------------- | ----------------------------------------------------- |
| 0      | uint8        | length        | Name byte length                                      |
| 1      | uint8[length]| string        | ASCII encoded name of *length* length                 |

*Names section* consists of above structure, tightly packed, repeated ``header:entries`` times.
Sum of their sizes is exactly ``header:names``.

## Contents

*Contents section* consists of chunks of data.
Each chunk is guaranteed to keep 8 bytes align - that is there are padding bytes added after names section and other data blocks if needed. 
Each chunk have different layout based on their *data type* (see *Index section*).
Chunks are guaranteed not to overlap, and to be in same order as their entries (lexicographical order by names).
Zero bytes chunk can begin at same position as following block (since it have zero size it does not overlap).

Chunks are placed as tightly as the alignment allows:
* First chunk has *data offset* ``0`` (the *Contents section* begins at the first byte after *Names* aligned to 8 bytes up)
* Every following chunk has *data offset* equal to the end of the previous chunk (its ``data offset + data bytes``)
    aligned to 8 bytes up. This applies to zero-length chunks too
* Bytes between the end of a chunk and the beginning of the next one are padding, and are zero
* Last chunk ends exactly at ``header:content``

## Footer

*Footer section* stores file checksum.

| Offset | Type     | Name      | Meaning                        |
| ------ | -------- | --------- | ------------------------------ |
| 0      | uint64   | checksum  | File checksum                  |
| 8      | uint8[8] | magic     | Magic sequence for correctness |

Checksum is generated according to specification above on byte range ``[first header byte, footer first byte)`` (inclusive/exclusive).
This range includes all padding, including the one between *Contents* and *Footer*.

Footer begins at the end of *Contents* (``content begin + header:content``) aligned to 8 bytes up, and is the last
16 bytes of the file.

## Data Types

*Data type* enumerator in *Index entry* informs reader how to interpret data stored in *Contents section*.
Following data types exists:

| Enumerator    | Name              | Layout                                                            |
| ------------- | ----------------- | ----------------------------------------------------------------- |
| 0             | Int               | Single int64 little endian value                                  |
| 1             | Float             | Single float 64 value                                             |
| 2             | Label             | Up-to 255 characters ASCII string of byte length as in entry      |
| 3             | Binary            | Block of bytes of byte length as in entry                         |
| 4             | Binary Compressed | uint64 holding uncompressed size and one ZSTD compressed frame    |

Constraints:

* *Int* and *Float*: data bytes is exactly ``8``
* *Label*: data bytes is at most ``255``, and every byte is in ``[32-126]``
* *Binary*: no constraints
* *Binary Compressed*: data bytes is at least ``8``. The compressed data is exactly one standard
    ZSTD frame (magic ``0xFD2FB528``) that spans all bytes after the uncompressed size: skippable frames, concatenated
    frames, legacy frames and trailing bytes are not allowed. The frame must uncompress to exactly
    ``uncompressed size`` bytes

## Malformed Files

Reader must reject the file as malformed if any of following is true:

1.  File is shorter than header and footer, or sections described by the header do not fit in the file
2.  Magic value in header or footer is wrong
3.  Header's ``entries`` count is greater than ``16'777'215``
4.  File does not end exactly at the end of the *Footer*
5.  Checksum does not match
6.  A padding byte is not zero (after *Names*, between chunks, between *Contents* and *Footer*)
7.  *Name offset* of an entry is not the one of *Index* section description, or *Names section* is not exactly
        ``header:names`` long, or a name exceeds the *Names section*
8.  Names are not in strictly increasing lexicographical order (this also covers duplicates)
9.  A name or a label has a byte outside ``[32-126]``
10. Data type is unknown, or data bytes violate the constraints of the data type
11. *Data offset* is not as described in *Contents*, or a chunk exceeds the *Contents section*
12. Header's ``content`` is not the end of the last chunk
13. A compressed entry is not as described in *Data Types*. This is detected when it is uncompressed

Files with ``version`` other than ``0`` are not malformed, they are of an unknown version.
